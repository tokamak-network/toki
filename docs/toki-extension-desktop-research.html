한 줄 결론

"얇은 익스텐션 먼저, 데스크탑은 나중." Toki에 맞는 정답은 데스크탑 + 얇은 익스텐션 하이브리드이되, 순서는 익스텐션 우선이다. 익스텐션은 Chrome/Firefox/Edge 도달 + 기존 Plasmo 익스텐션·EIP-1193 배선 재사용 + 클립보드 가드/OS 알림/상시 진입점을 훨씬 낮은 유지보수·보안 비용으로 제공한다. 데스크탑(Electron/Tauri)은 트레이 상주·글로벌 단축키·백그라운드 모니터링이 리텐션 동력으로 입증될 때, XSS→RCE 공격면 확대와 OS별 유지보수를 감수하고 도입한다.

01

권장 로드맵 — 3단계

기각 2건을 제외한 검증 사실 위에서 도출한 우선순위. Frame이 보여준 "무거운 네이티브 로직은 데스크탑, 얇은 인페이지 연결은 익스텐션" 하이브리드가 엔드게임이다.

Phase 1 · 지금

얇은 익스텐션

기존 Plasmo MV3 익스텐션 + getEthereumProvider() 배선을 그대로 확장.

  • EIP-6963 + EIP-1193 인페이지 연결
  • 클립보드 가드 (주소 스왑 방어)
  • 스테이킹 보상·가스 OS 알림
  • 상시 떠있는 진입점 (브라우저 액션)
Phase 2 · 검증되면

데스크탑 (Electron/Tauri)

트레이 상주·글로벌 단축키·백그라운드 모니터링이 리텐션을 끌면 도입.

  • 트레이/메뉴바 위젯 (Frame 패턴)
  • 백그라운드 잔고·APR·세뇨리지
  • 네이티브 알림 (OS별 경로 상이)
  • 하드닝 필수: contextIsolation 등
Phase 3 · 선택

스토어 배포

도달 채널 확대. 단, 스토어별 정책 함정 주의.

  • Chrome / AMO / Edge (익스텐션)
  • Mac App Store → 조직 계정 필수

가장 강력한 레퍼런스는 Frame. "무거운 네이티브 로직 = 데스크탑 프로세스, 얇은 인페이지 연결 = 익스텐션" 모델을 실증한다.

HighFrame 하이브리드 패턴3-0 ✓

Electron 메뉴바/트레이 상주 지갑이 시스템 전역에서 동작 + 로컬 JSON-RPC 엔드포인트(127.0.0.1:1248) 노출 + 별도 컴패니언 익스텐션이 레거시 dApp에 window.ethereum 주입.

05

보안 — 자가수탁의 핵심 뉘앙스

필수로 다뤄야 할 함의: 임베디드 지갑 키가 익스텐션/데스크탑 환경에 노출될 때 무엇이 안전하고 무엇이 안 안전한가.

✓ 안전한 것 — 키 자체

Privy 임베디드 지갑 키는 TEE에서 생성 → 2-of-2 share(enclave + Privy auth)로 분할 → 서명 시 격리 iframe/엔클레이브에서 순간만 재조립 후 즉시 폐기. 격리는 origin/process 기반이라 Electron/Tauri 웹뷰나 익스텐션 래퍼 안에서도 유지된다. → 키의 자가수탁은 익스텐션/데스크탑 껍데기에서도 보존된다.

✕ 안전하지 않은 것 — 트랜잭션 & 셸

"키 안전 ≠ 트랜잭션 안전." 침해된/악성 껍데기는 여전히 사용자를 속여 악성 트랜잭션 서명을 유도(headless signature·clickjacking)할 수 있다. 키를 못 빼가도 사용자가 잘못 서명하게 만들면 끝.

데스크탑은 공격면을 격상한다. 샌드박스 탭이 금지하는 파일시스템 접근·RCE로 XSS가 확대된다 (실제 CVE 다수, 2025.12 Trust Wallet 익스텐션 공급망 침해 $7M). 하드닝(contextIsolation:true, nodeIntegration:false, sandbox:true)은 완화일 뿐 제거가 아니다. Tauri로 옮겨도 위협 모델이 바뀔 뿐 사라지지 않는다.

지갑 보안은 공유 책임. 껍데기를 추가하는 순간 Toki의 로컬 공격면이 커지므로, 네이티브 이득과 저울질해야 한다. → 완화책: Privy 도메인 allowlist, 트랜잭션 MFA, Blockaid류 트랜잭션 스캐닝 (열린 질문 §07).

High클립보드 클리퍼 — 2026 실시간 위협2-1 / 3-0 ✓

복사한 암호화폐 주소를 공격자 주소로 OS 클립보드 레벨에서 몰래 바꾸는 멀웨어(형식/길이 패턴 매칭, ~500ms 폴링)가 현재 확산 중. 웹페이지는 이 방어를 원천적으로 못 한다 — W3C Clipboard API가 백그라운드 클립보드 읽기를 금지(포커스+제스처+HTTPS 필요)하기 때문. 따라서 "붙여넣기 시 주소 변경 경고" 가드는 웹 샌드박스 밖에서 돌아야 한다.

근거Microsoft Threat Intelligence (2026-06-17, 리포트 7일 전). Check Point 샘플 1건이 공격자 주소 15,500개+ 보유, Trust Wallet 연구 변종 1건 $560K+ 탈취. 선례: Opera "Paste Protection", MetaMask 주소 대조 권고. → Toki 클립보드 가드의 존재 이유 = 네이티브 껍데기.

네이티브 알림 & 트레이 — 검증된 패턴

High트레이 상주 + OS 알림3-0 ✓

데스크탑 빌드는 Toki에 상시 트레이/메뉴바 진입점 + OS 네이티브 백그라운드 알림을 준다 — 웹앱 불가능. Electron Tray API가 지속 아이콘+컨텍스트 메뉴 배치, Windows에선 tray.displayBalloon()으로 타입별 알림 발사. 실제 shipped: Frame은 메뉴바 상주, BlueWallet 데스크탑은 "대기/확정 트랜잭션 푸시 알림" 제공.

열린 질문 — 결정 전 확인할 것

타깃 사용자의 데스크탑 vs 모바일 분포는? 네이티브 form factor 논거는 데스크탑에서 가장 강하다. 입문자 다수가 모바일이면 익스텐션/데스크탑 도달이 적어지고 PWA/모바일 알림 경로가 더 중요해진다.

Privy 임베디드 지갑이 MV3 service-worker/content-script와 Electron/Tauri 웹뷰 안에서 정상 동작하나? EIP-1193 인터페이스는 확인됐지만, iframe 기반 키 재조립과 Google-OAuth 로그인 플로우가 비표준 브라우징 컨텍스트에서 도는지는 미검증.

키 격리로도 남는 트랜잭션 조작(headless-signature/clickjacking) 리스크를 어떻게 완화하나? Privy 도메인 allowlist, 트랜잭션 MFA, Blockaid류 트랜잭션 스캐닝 — 통합 비용은?

Mac App Store 경로: 조직이 D-U-N-S/조직 등록을 보유(또는 취득 가능)한가? 직접 .dmg/Homebrew 배포가 Apple 3.1.5 심사 마찰과 잠재적 3.1.5(iii) 거래소 라이선스 트리거를 피하는 더 나은 길인가?

기각된 주장 — 안티슬롭

3명 검증자가 만장일치(0-3)로 기각. 리포트에서 제외했지만 투명성을 위해 기록.

BlueWallet 데스크탑이 ElectrumX/Electrs 풀노드 연결을 데스크탑 전용 역량으로 제공한다.

✕ 0-3 기각 — 풀노드 연결이 데스크탑 폼팩터에 묶인 고유 역량이라는 주장은 입증 안 됨.

Privy가 Shamir Secret Sharing으로 device/auth/recovery 2-of-3 share 모델을 쓴다.

✕ 0-3 기각 — 활성 서명 share set은 2-of-2. 3-share 모델은 별개 레이어인 "복구(recovery)"를 설명한 것 (혼동).
